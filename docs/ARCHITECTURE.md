# 기능 구조 및 외부 연동 설계

이 문서는 공급처와 기술 스택을 고르기 전에 기능의 책임과 처리 경계를 확인하는 검토안이다. 아래 경계는 하나의 애플리케이션 안에서도 나눌 수 있다.

## 기능별 책임

| 기능 | 책임 |
| --- | --- |
| 지도 탐색과 대상 식별 | 주소·지번·건물명으로 위치를 찾고, 해당 위치의 등기 대상 후보와 식별 근거를 관리한다. |
| 문서 제출과 정보 공유 | 제출 자료의 파싱, 대상 확인, 마스킹, 검수, 공개 가능 여부, 버전을 관리한다. 화면에는 공유가 허용된 정보만 전달한다. |
| 관심 등록과 주기 조회 | 활성 관심 대상을 모아 고유번호별로 외부 확인을 실행하고, 성공·실패와 확인된 사건을 기록한다. |
| 알림 | 사건의 확인된 상태와 활성 관심 등록을 바탕으로 수신자를 정한다. 서비스 내 알림과 알림톡의 처리 결과를 채널별로 관리한다. |

## 공급처를 선택할 때 확인할 항목

| 연동 | 확인할 정보 | 미확정 결과를 처리하는 방식 |
| --- | --- | --- |
| 지도·주소 | 지원 검색어와 결과 식별값, 지번·도로명·건물 관계, 상세 주소 제공 범위 | 등기 대상에 필요한 정보가 부족하면 후보로만 표시한다. |
| 등기 자료 확보와 추출 | 공식 열람 연동 가능 범위, 파일 형식과 샘플, 필수 추출 항목의 검증 가능성 | 식별 또는 검수에 실패한 자료는 처리 상태를 기록하고 게시를 보류한다. |
| 변동 조회 | 요청 식별정보, 확인 가능한 사건·처리 상태, 사건 식별값과 시각, 과금, 장애와 제한 신호 | 확인할 수 없는 세부 항목은 확인되지 않은 상태로 남긴다. 해석할 수 없는 응답은 성공한 조회로 집계하지 않는다. |
| 알림톡 | 이용 조건, 수신 정보 처리 범위, 필요한 템플릿과 승인 절차, 발송 결과와 재시도 지원 | 서비스 내 알림과 채널별 발송 상태를 구분한다. |

공급처별 요청·응답과 오류 해석은 연결부에 둔다. 서비스 도메인은 확인 결과, 사건, 실패 사유를 받아 처리한다. 실제 공급처를 결정한 뒤 문서에서 확인한 요청·응답 예시와 지원 범위를 기록한다. 내부 검토에는 별도로 표시한 모의 공급자와 가상 사례를 사용할 수 있다.

## 변동 조회와 알림 처리 흐름

1. 확인 대상인 활성 관심 등록을 부동산 고유번호로 묶는다. 확인 주기에서 같은 대상이 일반 조회 대상으로 중복 선택되지 않도록 한다.
2. 대상별 결과를 기록한다. 응답의 출처와 확인 시각을 보존하고, 결과를 해석할 수 있을 때만 마지막 성공 시각을 갱신한다.
3. 새 사건이나 확인된 상태 변경을 식별해 저장한다. 같은 사건을 다시 받거나 작업이 재개될 때 기존 사건 또는 알림 예약을 재사용한다. 공급처가 사건 식별값을 제공하는지 확인한 뒤 중복 판정 기준을 정한다.
4. 발송 대상 수신자와 채널을 결정한다. 채널별 성공, 실패, 결과 미확인을 기록하고 현재 관심 등록과 채널 설정을 확인해 발송한다.
5. 일시 실패의 재시도는 공급처 제한과 과금 조건을 반영해 결정한다. 제출은 됐으나 응답을 놓친 알림은 발송 결과를 확인할 수 있는지 검토한 뒤 재시도한다.

## 운영 확인 항목

- 조회 대상 수, 실제 외부 요청 수, 조회 성공·실패 수와 마지막 성공 시각을 확인한다.
- 아직 해석할 수 없는 공급처 응답, 문서 검수 보류, 알림 채널별 실패를 확인한다.
- 예상 월 변동 조회비는 **평균 조회 대상 수 × 하루 확인 횟수 × 월 운영 일수 × 건당 단가**로 우선 추정한다. 월 기본료, 재시도, 묶음 과금, 문서 재열람, 알림 발송은 후보별 실제 과금 조건으로 추가 계산한다.
- 공급처, 확인 주기, 첫 조회 처리, 재시도 기준, 운영 지표 확인 책임자는 [결정 기록](DECISIONS.md)에 결정 근거를 남긴다.
