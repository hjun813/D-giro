# MVP 개발 계획서

이번 개발의 목표는 **실제 지도에서 위치를 찾고, 가상 등기 자료를 조회·공유하고, 가상 변동을 알림으로 확인하는 흐름**이 이어지는지 검증하는 것이다. 내부 검증 환경에서 지도 연동과 서비스 동작을 확인한 뒤 MVP 결과를 정리한다.

## 개발 범위

| 영역 | MVP에서 구현할 동작 | 데이터와 연동 방식 |
| --- | --- | --- |
| 지도와 검색 | 지도 표시·이동·확대, 주소·지번·건물명 검색, 검색 결과와 위치 마커 연결 | **실제 지도 API.** 카카오맵 JavaScript SDK를 1차 후보로 한다. |
| 등기 대상 선택 | 지도에서 위치를 고르고 토지·건물·집합건물 후보 및 동·호수를 선택 | 사전에 연결한 검증용 위치와 가상 등기 대상 목록. 공식 고유번호 매칭은 운영 단계의 검증 항목이다. |
| 등기 조회·공유 | 등기 자료와 권리관계 표시, 자료 선택·제출, 검수 상태, 중복 확인, 버전 갱신 | 앱이 제공하는 가상 PDF·이미지와 미리 정의한 추출·검수 결과를 사용한다. 제출, 검수 결과 반영, 버전 선택은 앱에서 처리한다. |
| 관심 등록·해제 | 가상 사용자별 관심 목록과 알림 상태 | 테스트 사용자 두 명을 전환해 같은 등기 대상을 구독할 수 있게 한다. 앱 상태에 등록·해제 결과를 저장한다. |
| 변동 조회·알림 | 대상별 중복 조회 방지, 접수·완료·미감지·실패 처리, 알림 생성과 읽음 | 내부 검증 화면에서 `변동 확인 실행`을 눌러 목 공급자의 다음 결과를 받는다. 상태 변경과 서비스 내 알림은 앱 로직에서 처리한다. |

운영용 등기 조회·변동 연동, 실제 등기 문서의 업로드·OCR·마스킹, 운영 회원가입·인증, 예약 조회 작업, 카카오톡 알림톡 발송은 MVP 검증 이후의 검토 항목이다. 시세·위험도·담보 분석 등 확장 기능은 [제품 로드맵](ROADMAP.md)에 기록한다.

## 지도 API 연동

1. 개발용 앱에서 카카오맵 사용 설정, JavaScript 키와 개발 주소의 도메인 등록, 해당 앱의 호출 한도와 과금 조건을 확인한다. 구현 착수 시 공식 가이드를 기준으로 설정한다. [Kakao 지도 Web API 가이드](https://apis.map.kakao.com/web/guide/) · [카카오맵 이용 조건](https://developers.kakao.com/docs/ko/kakaomap/common)
2. 지도 로딩과 이동·확대부터 확인한다. SDK의 `addressSearch`(도로명·지번)와 `keywordSearch`(건물명)를 사용해 검색 결과 선택 시 해당 좌표로 이동시키고 마커를 표시한다. [Kakao 지도 Web API 명세](https://apis.map.kakao.com/web/documentation/)
3. 공용 시설처럼 검색 가능한 검증용 위치 몇 곳을 내부 가상 사례와 연결한다. 주소·건물명 검색으로 같은 검증 위치를 찾아도 동일한 가상 대상 목록이 열리는지 확인한다. 가상 등기 대상과 문서에는 `검증용 가상 자료`를 표시한다.
4. 지원하지 않는 위치에는 `이 위치의 검증용 데이터가 없습니다`를 표시한다. 가상 대상 자체는 존재하지만 문서가 없는 경우에는 `공유된 검증용 자료가 없습니다`를 표시한다. 검색 결과 없음과 지도 로딩 실패도 각각 구분한다.

## 가상 데이터와 실행 방식

| 준비할 사례 | 검증할 동작 |
| --- | --- |
| 토지·건물 사례와 같은 위치에 연결한 가상 집합건물 두 호수 | 유형·동·호수 선택, 문서와 알림의 대상 일치, 호수 간 정보 분리 |
| 가상 문서 미등록·등록 완료, 대상 불일치, 검수 보류, 같은 문서 재제출, 이전 버전과 최신 버전 | 상세 표시, 잘못된 호수 연결 방지, 게시 상태, 중복과 버전 처리 |
| 변동 미감지 → 신청 접수 → 등기 완료 → 가상 새 문서 확보 | 접수와 완료 구분, 완료 시 갱신 필요 표시, 문서 반영 확인 후 해소 |
| 조회 실패, 같은 응답의 반복, 완료 뒤 늦게 수신한 접수 응답 | 마지막 성공 시각 보존, 알림 중복 방지, 오래된 상태로 되돌아가는 문제 검증 |
| 같은 대상에 관심 등록한 테스트 사용자 두 명, 한 명이 해제한 사례 | 확인 회차당 대상별 조회 1회, 활성 사용자에게만 알림 생성 |

목 공급자는 정해진 사례를 반환하고 앱은 결과에 따라 문서·관심 목록·알림 상태를 갱신한다. 최초 조회는 기준 상태를 기록하고 이후 회차에서 확인된 변화를 알린다. 테스트 사용자 전환과 초기화 동작을 제공해 같은 시나리오를 다시 실행할 수 있게 한다. 저장은 한 브라우저의 내부 검증 환경에서 가상 사용자별 상태를 구분하는 방식으로 시작한다. 실제 사용자 간 동기화와 서비스 운영 권한은 별도 검증 범위다.

## 구현 순서와 단계별 완료 기준

| 단계 | 작업 | 완료 기준 |
| --- | --- | --- |
| 1. 개발 준비 | 내부 검증에 필요한 웹 개발 환경을 정한다. 기존 로고를 연결하고, 지도·등기 대상·변동 결과의 데이터 경계를 정리한다. 지도 키 설정을 준비하는 동안 가상 사례를 작성한다. | 테스트 사용자와 검증용 위치·등기 대상·문서·변동 시나리오를 식별할 수 있고, 실행 환경에 지도 설정을 주입할 수 있다. |
| 2. 실제 지도와 등기 상세 | [UI 명세](UI_SPEC.md)에 따라 PC 패널과 모바일 시트를 만들고 지도 검색·선택과 가상 등기 상세를 연결한다. | 실제 검색으로 위치를 찾고 호수를 바꾸면 해당 호수의 가상 자료만 표시된다. 미지원 위치, 자료 미등록, 지도 실패가 각각 표시된다. |
| 3. 자료 공유와 버전 | 앱이 제공하는 샘플 선택, 제출, 검수 상태와 버전 전환을 연결한다. | 제출한 가상 자료가 검수를 통과하면 올바른 대상에 반영되고, 불일치 자료는 보류된다. 재제출한 문서나 뒤늦게 제출한 이전 문서가 있는 경우 기존 최신 버전을 유지한다. |
| 4. 관심 등록과 모의 변동 | 테스트 사용자 상태, 수동 변동 확인, 대상별 조회 기록, 앱 내 알림을 연결한다. | 같은 대상을 두 명이 구독해도 확인 회차당 목 조회가 한 번만 실행된다. 접수·완료·실패와 마지막 성공 시각이 구분되고 같은 알림이 반복 생성되지 않는다. |
| 5. MVP 인수 | 시작 데이터 초기화 후 대표 흐름을 PC와 모바일에서 재현하고 결과를 기록한다. | 아래 인수 흐름을 반복 재현할 수 있고, 실제 연동 범위와 모의로 검증한 범위가 결과에 드러난다. |

## MVP 인수 흐름

1. 실제 지도에서 주소·지번·건물명으로 검증 위치를 찾고, 같은 건물의 가상 호수 두 개를 번갈아 열어 자료가 섞이지 않는지 확인한다.
2. 한 호수에는 기존 가상 자료를 확인하고, 다른 호수에는 샘플을 제출해 검수 보류와 정상 반영을 재현한다. 같은 문서와 이전 문서를 추가로 제출해 버전 동작을 확인한다.
3. 테스트 사용자 두 명으로 같은 가상 대상을 관심 등록한다. 변동 확인 회차마다 대상 조회 횟수, 신청 접수·완료 알림과 반복 응답 시 중복 여부를 확인한다. 한 명이 해제한 상태에서도 실행해 현재 관심 등록에 따라 알림이 생성되는지 확인한다.
4. 조회 실패 때 마지막 성공 시각이 유지되는지 확인한다. 완료가 반영된 새 가상 문서가 검수를 통과한 뒤 갱신 필요 표시가 해소되는지 확인한다.
5. PC와 모바일에서 검색 결과·대상 상세를 열고 닫아 지도 위치와 검색어가 유지되는지 확인한다. 실행 환경, 실제 지도 결과, 모의 시나리오, 발견한 결함을 기록한다.

[검수 시나리오](ACCEPTANCE_TESTS.md)에서 지도·대상·문서 상태·알림 관련 항목을 골라 가상 사례로 실행한다. 실제 회원가입·권한 정책, 실제 문서 처리, 외부 메시지 발송과 자동 조회 조건은 운영 검증 때 확인한다. MVP 인수 결과가 나오면 이번 개발 범위를 닫고 운영 연동이나 확장 착수 여부는 별도로 판단한다.
